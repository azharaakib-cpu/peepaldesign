Design systems

A single, reusable set of components, patterns, and rules — so every screen your team ships looks and behaves like it belongs to the same product.

Build your design system

One place everyone trusts, not a folder of screens

What a design system is, and the four layers — tokens, components, guidelines, accessibility — that make it up.

Definition

“Design and code, building from the same parts.”

A design system is a shared set of reusable components, patterns, and design tokens — colour, type, spacing, iconography — paired with the rules for using them.

What's inside
Tokens
Colour, type, spacing, and iconography defined once.
Components
Buttons, forms, cards, navigation — every variant and state.
Guidelines
The rules for when and how each pattern is used.
Accessibility
WCAG standards baked into the base components.

Change a token, change everything

Tokens are the source, components are downstream. Move the accent or the corner radius and watch every component update at once — that's the whole point of a system.

Design once, reuse everywhere

Four ways one shared system pays for itself as the product grows.

Consistency at scale, not four different navbars. Every new screen inherits the same components and rules instead of being designed from zero, so a new hire's first screen still reaches for the same button, not a slightly different one nobody remembers approving.

Faster shipping, because nobody's rebuilding a dropdown. Teams build from existing patterns rather than reinventing basic components on every project — a sprint that would've gone on "does this input already exist" goes to the actual feature instead.

Easier collaboration, one source of truth. Design and engineering share the same source of truth, cutting down on handoff friction and rework — a spec that says "use the existing card" instead of a Figma file redrawing one that already ships in code.

Cheaper to maintain, one fix instead of forty. A single component updated once propagates everywhere it's used, instead of fixing the same thing across dozens of screens that have each drifted slightly apart since the last redesign.

How the system stays coherent

From tokens at the base to the governance that keeps the system from drifting.

01

Tokens before components

Colour, type, and spacing are defined once at the base as tokens, so every component inherits the same values automatically.

02

Documented variants and states

Every component ships with its variants and states spelled out, so nobody has to guess what a hover or disabled state should look like.

03

Accessibility at the base

WCAG standards are built into the base components themselves, not layered on top after a screen has already shipped.

04

One source of truth

Design and engineering build from the same system, in sync, so a component in Figma matches the one that ships in code.

05

Governed, not abandoned

Someone owns updates and additions to the system, so it stays coherent instead of drifting apart screen by screen.

06

Built to scale

The system grows with the product, not just today's screens, so new patterns extend it instead of working around it.
